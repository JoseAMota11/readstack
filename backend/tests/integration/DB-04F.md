# DB-04F: disposable PostgreSQL route validation

This is an opt-in test, excluded from `npm test`. It uses actual Express routes and PostgreSQL repositories on one client and rolls its synthetic writes back. It does **not** create, migrate, reset, truncate, delete or remove a database or container. The owner reports a successful disposable run and independent rollback check; see `PROGRESS.md`. DB-04 has qualified foundation acceptance, not production readiness. This test is not staging, production, full provider parity, or a DB-05 reset procedure.

## Separate owner authorizations required

Obtain explicit written approval, scoped to the specific new container ID, image digest, local port, database and role, for: (1) creating and starting that isolated container and its credentials/TLS material; (2) connecting to it and performing identity/catalog reads; (3) applying exactly the packaged `0001_initial_schema.sql` with the local migration runner to that initially empty database; (4) the harness's synthetic transaction and rollback, including API updates/deletes inside it; and (5) stopping/removing that exact container and its ephemeral resources after the run, including after failure. Approval of one does not imply any other. No production, Neon, Render, old rollback container, shared data, SQLite data or record transfer is in scope. Do not reuse a target with unknown history. If any approval or identity check is missing, stop.

## Target preparation and checks, only after approval

1. On a trusted local Docker daemon, prepare a **new** PostgreSQL 17 container with no mounts or volumes, no restart, an ephemeral tmpfs at `/var/lib/postgresql/data`, a single `127.0.0.1` port mapping to container port 5432, and database `readstack_disposable_db04f` and role `readstack_db04f_runner`. Record its full immutable 64-hex container ID and `sha256:` image ID; independently verify the approved image and local daemon. Do not use a superuser beyond what initial provisioning/migration needs; record any temporary elevated privileges and their removal. The harness does not prove role least privilege.
2. Enable PostgreSQL TLS using a short-lived local test CA and a server certificate containing IP SAN `127.0.0.1`; provision private keys only into the disposable container, not the repository. Trust the CA through `NODE_EXTRA_CA_CERTS` for the test process. `verify-full` is mandatory; no TLS bypass is supported. Ensure no other client can reach or modify this target during preparation and testing. Keep test passwords and keys out of command history, process arguments, logs, source control and issue reports; use a protected ephemeral environment, disable shell tracing, and remove secrets after use. Do not paste Docker inspect output: it can contain credentials.
3. **Before any SQL writes**, inspect the exact container ID and image, running state, restart policy, mounts, tmpfs, and loopback binding; verify the port belongs to that container, not a proxy or another service. Connect only with separate approval and independently check `current_database()`, `current_user`, `session_user`, server version, and that the public schema is initially empty. Verify the target is dedicated and contains no user data. Stop on any mismatch; names and empty tables alone do not prove disposability. Avoid time-of-check/time-of-use replacement by excluding other Docker operators and clients.
4. With migration approval, configure the documented `READSTACK_MIGRATION_*` variables in `README.md` for exactly the confirmed local endpoint, database and role. The CLI uses plaintext local TCP (`ssl: false`), so run it only on the approved isolated loopback endpoint. From `backend/`, run `npm run migrate:local:ts` once under an external wall-clock timeout. It writes the schema and ledger. Independently verify that the ledger is exactly the packaged migration and checksum, and that users, books and reviews are empty. Do not repair, reset, or retry an uncertain migration without new approval. Application readiness additionally checks the packaged ledger and a limited schema subset; it is not a complete drift check.
5. Before the harness, repeat container/image/port checks and database/session-role identity and empty-data checks. Set an environment without inherited `PG*` variables. Set `DATABASE_PROVIDER=postgres`, `POSTGRES_TLS=verify-full`, `DATABASE_URL` to the approved `127.0.0.1` endpoint and the exact database/role, `DB04F_CONTAINER_ID` to the full ID, `DB04F_IMAGE_ID` to the image ID, and `DB04F_APPROVED=yes` only after the approvals above. Inject the URL and CA path securely; URL query options are rejected. The harness generates an ephemeral JWT key in memory. Never print the environment. Run from `backend/`:

   ```sh
   timeout --signal=TERM --kill-after=10s 140s node --import tsx tests/integration/postgres-routes.ts
   ```

   The executable rejects missing approval, non-loopback endpoint, mismatching fixed role/database, container/image/port/tmpfs identity or nonempty application tables before its first write. It rechecks container identity before `BEGIN`. This is defense in depth, not proof that the target has no other data or that Docker/loopback cannot be redirected. The operator must check identity **before migrations**, and must isolate the target from races.
6. The client uses 5-second connection/query/server-statement bounds; container inspection is bounded to 5 seconds, the whole harness to 120 seconds, and the external watchdog to 140 seconds plus 10 seconds kill grace. A timeout or lost connection does not prove rollback, server cancellation, or client shutdown. On success the transaction is rolled back; on failure or interruption, stop and isolate the target. With separately approved read access, verify application tables empty after exit. Never assume rollback after a timeout or uncertain outcome. Remove the exact approved disposable container and ephemeral TLS/secret materials only with the removal approval, including after failure; otherwise leave isolated and report it. No automatic resource removal is performed. Cleanup is therefore conditional, not guaranteed by the harness.

## Coverage and remaining gates

The DB-04F harness covers registration/login, unauthenticated/invalid token, basic CRUD, cross-owner book/review denial, malformed read IDs, ASCII search, `%`/`_`, genre, pagination, order, favorite mutation, timestamp format, review mutation and CSV. It uses one transaction, so it does not exercise production pool lifecycle, independently committed visibility, multiple connections, concurrency, or independent timestamp ordering. It tests one wildcard and genre subset, not full SQLite parity. Subsequent owner-reported DB-04G/I results cover selected lifecycle, escaped genre, Unicode and real database-error cases; see `PROGRESS.md` for their limits. CSV escaping, all TLS/lifecycle failures and staging remain beyond this harness's evidence. Never treat a mock pass or a prepared script as live evidence.

Checks executable without PostgreSQL: `npm test`, `npm run test:security`, `npm run build` (synthetic SQLite and fake clients); `node --import tsx --test tests/integration/postgres-guard.test.ts` uses a stub Docker executable to exercise missing approval, a remote URL and a mismatched container before any connection; and, with approval variables absent, `env -i PATH="$PATH" node --import tsx tests/integration/postgres-routes.ts`, which must fail closed before Docker or network access. These guard checks are not a live integration run and do not exhaustively test every identity check.
