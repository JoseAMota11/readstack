# DB-04I: opt-in live parity and security harness

Prepared only; **not executed against PostgreSQL**. DB-04 remains open. `postgres-parity-security.ts` is not part of `npm test`; the included guard unit test never connects to Docker or PostgreSQL. SQLite stays the default. No existing container or past approval is presumed valid.

## Separate written owner approvals

Before any operation, obtain written approval identifying the exact new disposable container's full immutable ID, image ID/digest and independently verified PostgreSQL 17 image, local Docker daemon, loopback port, database `readstack_disposable_db04i`, and role `readstack_db04i_runner`. Separately authorize: (1) provisioning that specific isolated container, credentials and TLS material if needed; (2) Docker inspection and PostgreSQL TLS connections and read-only identity, catalog, ledger, table and session checks before and after; (3) applying exactly the packaged `0001` migration to the independently confirmed empty target if it is not already prepared; (4) this harness's synthetic writes, updates, deletes, deliberate division-by-zero query, savepoints and rollback; (5) stopping/removing the exact container and its ephemeral resources, including on failure. No one approval implies another. Written approval is not replaced by `DB04I_APPROVED=yes`. Do not access production, Neon, Render, staging, SQLite records, shared data or historical targets; do not transfer records. If an approval or check is missing, stop.

## Independent preparation and isolation

Follow the target preparation and safe credential/TLS instructions in `DB-04F.md`, substituting the DB-04I database and role. Only after each applicable approval, use a new isolated PostgreSQL 17 container, no mounts/volumes, no restart, tmpfs for `/var/lib/postgresql/data`, and exactly one `127.0.0.1` binding to port 5432. A locally trusted short-lived CA and certificate with IP SAN `127.0.0.1` are required; TLS verification must not be disabled. Independently verify the full container ID, image ID and image provenance, daemon, port ownership (no proxy/forwarding), runtime configuration, server version, current database, current and session roles, and that the target contains no unrelated data. Confirm the ledger contains exactly the packaged `0001` filename and checksum, all three application tables are empty, email uses `C` collation, and there are no unrelated sessions on the database. Check `pg_stat_activity` with a suitably privileged independent read-only observer; disconnect that observer before execution. Restrict other local users, Docker operators, and clients from reaching or changing the target throughout, including between checks and writes. A count without visibility privileges is insufficient. Do not repair, reset, retry an uncertain migration, or reuse an unknown target.

The harness rechecks container ID/image/binding/tmpfs, database/role, packaged readiness ledger and limited schema, `C` collation, empty application tables and same-database sessions before writing. It requires `pg_read_all_stats` membership or superuser to establish session visibility; this requirement is not an endorsement of a superuser application role. These checks cannot prove image provenance, other databases' data, complete schema integrity, absence of a port proxy, or prevent time-of-check/time-of-use races. The owner must independently verify those boundaries. If isolation cannot be established, stop.

## Invocation after approval and checks

In a private shell with Node 22, existing dependencies and no inherited `PG*` variables, disable shell tracing. Securely supply `DATABASE_URL` (exact local host/port/database/role; no query options), and trust the local test CA via `NODE_EXTRA_CA_CERTS`. Keep credentials out of history, arguments, logs and shared process environments; never print Docker inspect output or environment. Set `DATABASE_PROVIDER=postgres`, `POSTGRES_TLS=verify-full`, `DB04I_APPROVED=yes`, `DB04I_CONTAINER_ID` to the full approved ID, `DB04I_IMAGE_ID` to the approved `sha256:` image ID, and `DB04I_PORT` to the approved decimal port. From `backend/` run:

```sh
timeout --signal=TERM --kill-after=10s 140s node --import tsx tests/integration/postgres-parity-security.ts
```

The process creates a synthetic in-memory JWT key and a loopback-only ephemeral HTTP listener. It does not create, migrate, reset or remove resources. It uses 5-second Docker, connection, server statement, driver query and HTTP bounds, a 120-second watchdog and the external timeout above. The one PostgreSQL client uses one transaction and savepoints; cleanup attempts listener close, rollback and client shutdown. A timeout, lost connection, forced termination or failed cleanup does **not** establish rollback or session closure. On any failure or interruption isolate the target; do not retry or remove it without the corresponding approval. After success **or failure**, independently recheck exact container/endpoint, identity, original ledger/checksum, empty users/books/reviews, and absence of runner/test sessions. Remove the specifically approved resources and secret material only with separate authorization. Never assume cleanup succeeded.

## Scope and limitations

The same DB-04H matrix is evaluated on synthetic in-memory SQLite and the real PostgreSQL book repository, including ASCII and Unicode, wildcard patterns, year and escaped JSON genres. The harness checks JSONB round-trip, case-distinct registration/login and duplicate response, token-owner cross-user denial, malformed endpoint responses, and one deliberately induced real PostgreSQL division-by-zero error propagated through the book-list HTTP route. That fault replaces the repository's query via an adapter; it is not a network failure or evidence for every route, error type or server log. Existing disconnected fake-client tests cover additional paths. Assertion failures are intentionally reported generically to avoid disclosing driver details; investigate only with separately approved, safe diagnostics.

One uncommitted transaction cannot establish committed multi-session visibility, concurrent uniqueness, pool behavior or independent isolation. It does not retest DB-04F/G lifecycle, TLS failures or complete endpoint coverage. A prepared harness or a fake-client pass is not live evidence, production readiness, staging approval or DB-04 completion. Any real parity mismatch remains a blocker for owner review, not authorization to change the API contract.
